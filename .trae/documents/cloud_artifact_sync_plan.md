# Cloud Streamlit 接 GHA Artifact v5 (A1) Implementation Plan

---

## 一、Repository Research（現況與問題邊界）

### 1.1 上游供應鏈（已穩定，本方案不修改）
- GHA 15 分鐘 cron 機制已達成全綠燈，每次 run 產生並上傳 `ohlcv-cache-artifact-v5` 壓縮檔。
- 壓縮檔內含單一檔案 `ohlcv_cache.sqlite`：已啟用 WAL 模式、3 表 schema 完整、有效快取 ≥ 8 支港股（0001/0700/2318 等）。
- 快取品質經 GHA Summary 雙層保護驗證：last_close 與 last_trade_date 無空值，與 Top 8 快取後設中繼資料 100% 一致。

### 1.2 下游瓶頸（本方案欲解決）
Streamlit Cloud 為單進程架構，無法常駐 daemon 累積快取，導致：
- `get_data_v7` StepA 的 L2 SQLite 快取在 Cloud 端永遠落空
- 被迫退回 fallback live Yahoo 模式：載入慢、外部請求量大、有 429 限流風險
- 與 GHA 已累積的有效快取完全斷鏈，造成雙端重複勞動

### 1.3 已驗證可行的介接前提
1. **插入點正確性**：`app.py` 與 `app_mobile.py` 的 cache_layer 初始化流程為「匯入 API → 呼叫 ensure_schema → 設定 OK flag」。替換 SQLite 檔 **必須** 在呼叫 ensure_schema 之前完成，避免 WAL 連線鎖定後無法置換檔案。
2. **Schema 相容性**：`cache_layer.ensure_schema` 設計為幂等操作，僅補齊缺表/索引、不破壞既有資料；GHA 端與 Cloud 端 schema 版本同源，直接可讀。
3. **API 路徑可行性**：不依賴 gh CLI，單純以 HTTP 請求 + 標準庫解壓縮即可完成 artifact 下載，適合 Cloud 無額外工具的環境。
4. **檔案系統可寫性**：Cloud 端 `data/` 目錄可由 `get_cache_db_path()` 自動建立；暫存解壓使用作業系統臨時目錄，不污染專案。

## 三、Implementation Steps（依賴順序，4 步驟）

### Step 1：底層便捷方法補齊（僅於缺失時執行）
- 目的：提供統一入口讀寫 `fetcher_stats` 表的自訂鍵值組
- 內容：
  - 針對 `fetcher_stats` 表新增讀取與寫入兩個便捷操作
  - 值自動進行 JSON 序列化與反序列化
  - 邊界：不動表結構、不加新欄位、不影響既有的 daemon 統計寫入邏輯

### Step 2：`app.py` 端 artifact 同步鏈接入
- 目的：在 cache schema 初始化前完成 SQLite 替換，確保後續所有快取讀取命中 GHA 帶來的資料
- 內容分四層：
  1. **Token 讀取層**：優先讀環境變數、備援讀 Streamlit Secrets；兩者皆無則跳過整個同步流程
  2. **下載與驗證層**：依序完成「取得最新 artifact 位址 → 下載壓縮檔 → 解壓至臨時目錄 → schema 相容性驗證 → 有效快取數量驗證」；任一關卡失敗直接中止，不碰既有 DB
  3. **原子替換層**：通過所有驗證後，以同磁碟移動操作將臨時 DB 覆蓋至正式路徑，避免半寫入毀損
  4. **頻率保護層**：兩道閘門（快取裝飾器 9 分鐘 TTL + fetcher_stats 表同步時間戳雙重檢查），避免連續 reload 重複下載
- 後續處置：
  - 成功：記錄狀態旗標、時間戳、有效快取數；接續執行既有的 ensure_schema
  - 失敗：關閉同步旗標、記錄警告日誌；接續執行既有的 ensure_schema（等於退回舊架構）

### Step 3：`app_mobile.py` 完全鏡像 Step 2
- 目的：雙端行為一致，手機使用者亦獲得相同的快取命中體驗
- 內容：Step 2 的所有邏輯 1:1 移植，僅狀態變數加上對應後綴以避免命名衝突；TTL、失敗處置、驗證門檻完全相同

### Step 4：Sidebar 隱藏狀態區加入
- 目的：提供除錯可見性、但不破壞既有 UI 版面
- 內容：
  - 擺放位置：sidebar 既有內容的**最下方**
  - 呈現方式：HTML details 標籤，預設摺疊
  - 三種狀態文字：
    - 同步成功：顯示同步時間、有效快取數、當前命中模式
    - 同步失敗：顯示降級提示與錯誤類型（僅摘要、不顯示敏感資訊）
    - 未設定 Token：顯示提示並主動關閉同步流程
- 邊界：**不移動、不修改、不遮蔽 sidebar 任何既有元素**

## 四、Dependencies and Considerations（約束與注意事項）

### 4.1 絕對保留的既有約束（本方案完全不碰）
1. Yahoo 請求節奏 0.8–1.6 秒抖動
2. Route1 Yahoo → Route2 yfinance → Route3 Stooq → Route4 Sina 降級順序
3. 15 分鐘內 429 ≥ 4 次即全域降溫 600 秒
4. SQLite WAL 模式啟用

### 4.2 UI 不變承諾
- 使用者可見的首頁、比較頁、回測頁、任何圖表/表格/按鈕**一字不改**
- A1 相關資訊僅存在於 sidebar 最下方摺疊區；預設狀態下使用者看不到任何差異

### 4.3 資訊安全約束
- Token 僅來自環境變數或 Streamlit Secrets，**程式碼中絕不硬編碼任何金鑰**
- 日誌與狀態顯示僅呈現網域、HTTP 狀態碼、錯誤摘要；**永不記錄或顯示 Authorization 標頭內容**

### 4.4 執行順序剛性要求
- 嚴守「先替換 DB 檔 → 再建立 SQLite 連線」的順序；若顛倒會導致 WAL 鎖定、替換失敗或資料損毀

### 4.5 雙端一致性要求
- `app_mobile.py` 的行為閾值（TTL 時長、有效快取數門檻、失敗處置策略）**必須與 `app.py` 完全相同**，不得出現手機端執行更頻繁或驗證更寬鬆的狀況

## 五、Validation（驗證清單，5 + 2 項）

### 5.1 Acceptance Criteria 五項核心驗證
1. **(a) 本機模擬下載成功**：
   - 設定有效 Token 後首次啟動，SQLite 檔案大小顯著成長（> 200KB）
   - 快取層可讀出至少 8 支港股，包含 0001.HK、0700.HK、2318.HK 等核心標的
2. **(b) Cloud 端首頁快取命中**：
   - 完成部署三件套（Reboot → Clear cache → Redeploy）後
   - 首頁直接造訪 0700.HK，狀態顯示為命中模式而非即時下載模式
   - sidebar 同步狀態顯示成功
3. **(c) 失敗情境優雅降級**：
   - 人為使 Token 失效或刪除遠端 artifact 後，首頁仍正常開啟、股價數據正常顯示
   - 無崩潰、無異常堆疊、無任何使用者可見的錯誤中斷
   - sidebar 狀態正確顯示降級提示
4. **(d) 9 分鐘頻率保護生效**：
   - 連續重新載入 10 次頁面，觀察日誌或外部呼叫紀錄，實際發出的 artifact 下載請求 ≤ 1 次
5. **(e) 雙端行為一致**：
   - 桌面版與手機版在相同啟動條件下顯示相同的同步狀態文字、相同的有效快取數
   - 兩端皆能命中同一批 GHA 帶來的快取資料

### 5.2 額外迴歸驗證
6. **底層穩定性**：既有的 7 項 `test_cache_daemon.py` 測試全數通過
7. **語法正確性**：3 個變更檔案直譯器檢查零錯誤

## 六、Risks（風險與緩解對策）

| 風險項目 | 影響 | 緩解對策 |
|---------|------|---------|
| **R1：Token 權限不足或 API 回傳 403/404** | 同步失敗，但不影響舊功能 | 直接觸發優雅降級；狀態顯示錯誤摘要；引導使用者確認 PAT 需勾選 repo 級 Actions 讀取權限 |
| **R2：壓縮檔或 SQLite 檔案損毀** | 同步中止，但不毀損既有 DB | 先完成所有驗證再進行覆蓋；不通過驗證則直接捨棄臨時檔案、不碰正式路徑；下次 TTL 到期自動重試 |
| **R3：多使用者同時連入導致競態覆蓋** | 極端情況下可能短暫讀取不一致 | 雙層 TTL 閘門壓縮同時下載機率；覆蓋前檢查目標檔案最後修改時間，若已在同步窗口內則跳過；檔案系統移動操作本身具原子性 |
| **R4：Cloud 端重啟導致檔案遺失** | 下次啟動時需重新下載，數秒落差 | DB 存放路徑避開臨時目錄；即使遺失，下次首頁載入自動觸發重新同步，5–10 秒內自動恢復快取命中 |
| **R5：未來 artifact schema 與 Cloud 端版本落差** | 同步失敗 | `ensure_schema` 幂等補齊缺表/索引；若仍不相容則不放行覆蓋，維持舊版 DB + 優雅降級；待兩端版本一致後自動恢復 |
